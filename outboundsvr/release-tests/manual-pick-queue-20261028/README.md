## Behavior

- New sales orders do not reserve stock on creation/import. Users must complete Allocate first. Missing reservation or request failures never fall back to CLASSIC.
- The one-time legacy allowlist preserves orders that already had Picks or short allocations. An empty shipment does not create a legacy exception. The migration marker makes the supplied SQL safe to rerun without admitting newer orders.
- Continuous scan applies to ITEM_QUANTITY orders. The server commits a prepared Pick (and converts held quantity) and durable queue row in one transaction before returning acceptance. Acceptance is NOT final movement confirmation; it still includes validation and Pick preparation, so no sub-second latency promise is made.
- A separate worker completes movement/confirmation with the existing stable UUID and Inventory idempotency. Queue row locking prevents duplicate workers. Committed completion survives response loss/restart. A failed task pauses its order and retains the saved Pick/quantity for explicit recovery; it is never silently released or recreated.
- At most 30 waiting tasks per order. Scope/client checks remain enforced. No user token is stored. Original operator attribution is preserved. Worker-only HTTP timeouts: connect 3s, response 15s. Ordinary synchronous HTTP behavior is unchanged.
- Mobile clears the scanner only after server acceptance, shows per-pallet states, preserves uncertain requests, restores the last queued order, and refreshes RF inventory/remaining quantity on completion. Partial pallets retain the quantity/new-label confirmation dialog.
- Unpick displays a pressed/loading state before mounting its dialog, guards missing detail fields and duplicate submissions, waits for confirmation before closing, and retains the dialog on errors. No claim is made that the separate server-side Unpick inventory movement is faster.
